## 2. Five largest deviations from the approved concept

1. **The Lesson Workspace and its three Views do not exist.** The approved concept is «1 bài học – 3 cách học»; the build has zero View code (no segmented control, no Smart Book page rendering, no Trực quan renderer, no in-lesson SAM). `16-UX-CONCEPT.md` is explicitly «a HYPOTHESIS … not a spec» (line 10). Status: **concept-no-code**.
2. **«Học với SAM» is one lesson, rules-only, and unreachable for the Founder's learner.** The tutor engine is real and doctrine-safe, but hints are 6 templates (`slice_curriculum.dart`), the registry has one row (`:114-118`), there is no model/network call anywhere in `lib/` (pubspec has no HTTP client), and for lớp 6 the only entry (camera) fails closed. The Home ask-bar says so on screen: «SAM đang học cách trò chuyện».
3. **Home tells a grade-6 child SAM has no content, and the button on that card opens the camera.** `buildMissionFromStore` reads only the Toán 5 Deep path (`mission_data.dart:203-229`); KHTN 6 lessons open fine from the shelf; a KHTN session recorded during this audit did not change Home (audit-16). Progress then shows «có SAM giúp 1 phiên» next to «chưa có bằng chứng học nào» (audit-23).
4. **Provenance surfaces leak internals and cross grades.** Toán 6 «Hình trong sách» shows a Toán 5 page asset; source lines print raw ids (`06-sgk-ngu-van-6-tap-mot`, `khtn`); MapReader hard-codes «SGK … 5». The concept and `PEDAGOGICAL-PROVENANCE-UX` require child-facing wording and a page-image lookup sheet — the sheet does not exist.
5. **No chapter level, no book header, no bottom navigation.** Concept-chuong frames 3–4 (Chương → Bài with state) and both concept boards' tab bar are absent; the build is Home → shelf → flat list → activity, with Tiến bộ / Bản đồ / Phiên học / Hồ sơ / TKB tucked under «…» (audit-22). Duplicate «Đọc bài» rows in the activity sheet (audit-06) remain the first thing a KHTN-6 learner meets.

## 4a. Process notes — exact sequence that led to the device lock

All inputs were `adb -s 192.168.1.3:5555 shell input …`; no `keyevent 26` (POWER) or `82` (MENU) was ever sent.

1. ~10:24 Home (scrolled) → tap «Bố mẹ ▸» → PIN set-up screen (audit-32) → `keyevent 4` (only dismissed keyboard, audit-32b) → tap «Quay lại» → Home (audit-33).
2. ~10:25 tap decision-card «Bắt đầu» (246,1095) → app pushed the camera flow → Android permission dialog `GrantPermissionsActivity` (audit-17).
3. `keyevent 4` once — dialog stayed in focus.
4. ~10:26 tap «TỪ CHỐI» (540,1215) — deny once.
5. ≈2.5 s later: screencap came back blank, `mCurrentFocus=StatusBar`; `dumpsys power` → `mWakefulness=Dozing`, `Display Power: state=OFF`; app pid alive; logcat showed only the camera HAL releasing (`QCamera … stop inactive channel`). No lock/power input had been sent — the display went to sleep on its own (most consistent with the device's idle timeout coinciding with the permission-denial transition; not proven).
6. Diagnostics only (`pidof`, `dumpsys window/power/trust`): keyguard up, `deviceLocked=1`.
7. `keyevent 224` (WAKEUP) → lock screen with clock + notifications; one swipe-up (540,1700→500) to test for a swipe-only keyguard → screen dozed again.
8. `keyevent 224` + one swipe-up → **pattern grid** visible (audit-34c). **Stopped here.** No pattern drawn, no further input. The lock-screen frame that showed the Founder's notifications was deleted from the evidence folder.

Lesson for the protocol: after any system dialog (permissions), re-check `dumpsys power` before the next tap, and treat a blank screencap as "display off", not as an app state.
